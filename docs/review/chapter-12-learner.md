## Method

The same two personas as in the reviews of chapters 2 to 10 went through all 33 steps.

- **The copier** reads the code card and the delete boxes, pastes the highlighted lines at the place the fence shows, and builds at each checkpoint. Checked: is the place clear, is anything needed that no step says (import, Xcode action, deletion), do the delete boxes cover every line that `git diff chapter-11 chapter-12` removes or changes, is any line highlighted in two steps, does a highlighted run contain a line that already exists on `chapter-11`.
- **The self-implementer** uses the "Try first" mode. This person sees the instruction, the caption, the cover (file, "Inside …", context lines, placeholders, the comment lines of the solution as hints, delete box), and the Swift notes, but not the code. Checked: does the text give each new identifier with its type, access level, start value, and parameters; does it name each API class (`AVCaptureControl`, `AVCaptureSystemZoomSlider`, `AVCaptureSystemExposureBiasSlider`, `AVCaptureSlider`), each delegate method of `AVCaptureSessionControlsDelegate`, the session queue rule (`setActionQueue(_:action:)` and `setControlsDelegate(_:queue:)` with the actor's executor), and the log texts; does the text say when the project does not compile or builds with warnings between steps.

The cover text of each of the 28 code steps was extracted from the rendered HTML (29 "Inside …" texts; the two covers at file level have none) and compared with `git diff chapter-11 chapter-12` and `git show chapter-12:AVCam/CaptureService.swift`. The findings were fixed on the page in the same pass (captions only; no instruction, main code fence, `remove` fence, or `copy` mark changed, because the chapter has no new file and no boilerplate). Then `npm run validate` and the replay ran.

## Suggestions for the generator and the glossary

1. **Glossary: the in-out projected value `&$property`.** Step 4.2 writes `.assign(to: &$isShowingFullscreenControls)`. The `inout` entry matches only the keyword, so a learner gets no card for `&` with a projected value. A short entry (pattern `/&\$\w+/`, title "&$name (in-out projected value)", text: "`$name` is the publisher of a `@Published` property. `&` passes it in-out, so `assign(to:)` can keep the subscription in it.") would help. The first use is probably `observeOutputServices()` in an earlier chapter; check with `grep -n '&\$' content/pages/*.md`.
2. **Generator: a step that breaks a protocol conformance.** Step 4.4 adds a requirement to `Camera`, and the project does not compile until 4.6. The same pattern was on chapter 9 (section 4). A fence attribute such as `compiles=no` or `warnings` (see the chapter 9 review, suggestion 2) would render a standard note instead of a caption sentence.
3. **Generator: string literals and symbol names.** Four findings here are string values (a title, an SF Symbol name, two log texts) that only the solution shows. The cover already shows comment lines as hints. It could also show string literals of the highlighted lines in the hint style ("the step uses the strings: …"), so that captions need not repeat them.
4. **Replay: the `claims` flag.** Section 5 prints `claims=n` because the Experiment, Note, and Text items follow the last checkpoint (same as the chapter 9 review, suggestion 4). The section builds.
5. **Validator: white-space-only changes.** The diff for `MainToolbar.swift` has one line that changes from empty to four spaces. The validator ignores it by rule, and the replay too. A note in the validator output ("1 white-space-only change in <file>") would tell the writer to mention it, as finding 12 now does by hand.
