## Method

The same two personas as in the reviews of chapters 2 to 16 went through all 46 steps.

- **The copier** reads the code card and the delete boxes, pastes the highlighted lines at the place the fence shows, and builds at each checkpoint. Checked: is the place clear, is anything needed that no step says (import, Xcode action, target membership, deletion), do the delete boxes cover the 13 lines that `git diff chapter-16 chapter-17` removes and nothing else, is any line highlighted in two steps, does a highlighted run contain a line that already exists on `chapter-16`, does a context line exist at the time of the step.
- **The self-implementer** uses the "Try first" mode. This person sees the instruction, the caption, the cover (file, "Inside …", context lines, placeholders, the comment lines and the string literals of the solution as hints, delete boxes), and the Swift notes, but not the code. Checked: does the text give each new identifier with its type, access level, start value, `throws`, parameters, and argument labels; does it name the multi-camera API (`AVCaptureMultiCamSession`, `isMultiCamSupported` of the session and of a format, `addInputWithNoConnections(_:)`, `ports(for:sourceDeviceType:sourceDevicePosition:)`, `setSessionWithNoConnection(_:)`, `AVCaptureConnection(inputPort:videoPreviewLayer:)`, `canAddConnection(_:)`, `addConnection(_:)`, `hardwareCost`, `systemPressureCost`, the format selection with `formatDescription.dimensions.width` and `maxFrameRate`, `isVideoMirroringSupported`, `automaticallyAdjustsVideoMirroring`, `isVideoMirrored`, `RotationCoordinator`, `videoRotationAngle`), the `UIViewRepresentable` container with its layout values (0.3, 16 points, corner radius 12, border 1 point, 0.25 seconds, `resizeAspectFill`, `safeAreaInsets.top`), and the picker width (240 and 180); does it say when the project does not compile or builds with warnings between steps.

The cover text of each of the 39 code steps was extracted from the rendered HTML (35 "Inside …" texts; the two new-file covers 2.1 and 3.2 and the two top-level covers 3.3 and 5.1 have none) and compared with `git diff chapter-16 chapter-17 -- '*.swift'` and `git show chapter-17:<path>` of the files. The replay ran one time before the fixes, to see what a copier gets, and one time after. The findings were fixed on the page in the same pass (captions, and the two `remove` fences of step 4.7 became three; no instruction, main code fence, or `copy` mark changed, because the two new files are not boilerplate). Then `npm run validate` and the replay ran.

## Suggestions for the generator and the glossary

1. **Glossary: tuples.** Step 2.6 compares two tuples with `<` inside `max(by:)`, and step 4.1 declares an optional tuple type with labels, `(back: …, front: …)?`. No entry matches either. Suggested entries: pattern `/\(\s*[^()]+,\s*[^()]+\)\s*<\s*\(/`, title "Tuple comparison", text: "Swift compares two tuples element by element, from left to right. The first element that differs decides." And pattern `/:\s*\(\s*\w+:\s*[\w.]+,\s*\w+:\s*[\w.]+\)\??/`, title "Tuple type with labels", text: "A tuple groups values without a new type. With labels, the code reads `layers.back` instead of `layers.0`." Link: the Swift book, "The Basics", Tuples.
2. **Generator: a step that breaks the build.** This page has six places where the project does not compile until a later step (2.2, 2.3, 3.2 to 3.5, 4.3, 5.3) and one warning (4.5). The `compiles=no` or `warnings` fence attribute from the chapter 9, 12, 14, and 16 reviews would render a standard note instead of a caption sentence in each place.
3. **Validator: a delete box that lists a context line.** Finding 1 is a `remove` fence line that is also a non-highlighted line of the main fence of the same step. The validator could give a warning when a trimmed line of a `remove` fence equals a trimmed context line of the main fence, because a copier deletes it and nothing adds it back. The replay cannot see it, because git keeps the line.
4. **Generator and replay: a highlighted brace that already exists.** Finding 5 is the same pattern as chapter 16, suggestion 6, in a new form: git aligns the old closing brace of `PreviewTarget` with the new closing brace of `DualPreviewSource`. The replay reports "unclear (brace position)" and accepts it, but a copier gets the extraneous brace for real. A generated hint on a highlighted line that is only `}` and whose text equals the next unchanged line of the start branch ("git counts this brace as new; your file has it already") would replace the caption sentence. The replay could treat this case as a copier problem and not as unclear.
5. **Generator: a context line that a later step adds.** Finding 4: the fences of 3.4 and 3.5 show the closing brace of `DualPreviewContainer` as a context line, but 3.6 highlights it. The cover says "The lines below are already in your file", which is wrong for that brace. The validator knows which context lines a later step highlights (it works from the last step back); the cover could mark such a line ("a later step adds this line") or leave it out.
6. **Generator: argument labels.** Findings 6, 10, and 13 depend on labels (`backCamera:frontCamera:backPreview:frontPreview:`, `back:front:`) that only the solution shows. As in the chapter 16 review (suggestion 5), the cover could list the labels of a new method signature in the hint style.
7. **AUTHORING: a `new` fence that shows a part of the file.** The rule says "Show the complete file", but 2.1 and 3.2 show the first part and the later steps add the rest, which the validator accepts and which is better for the learner. The rule could say so: "or the first part of the file, when later steps add the rest".
