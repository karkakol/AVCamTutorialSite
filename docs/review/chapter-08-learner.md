## Method

- **The copier** reads the code card and the delete boxes, pastes the highlighted lines at the place the fence shows, and builds at each checkpoint. Checked: is the place clear, is anything needed that no step says (build setting, import, Xcode action, deletion), do the delete boxes cover every line that `git diff chapter-07 chapter-08` removes or moves, is any line highlighted in two steps. This chapter changes five views, the capture service, and the two models, so moved lines and replaced blocks were the focus.
- **The self-implementer** uses the "Try first" mode. This person sees the instruction, the caption, the cover (file, "Inside …", context lines, placeholder, delete box, copy note), and the Swift notes, but not the code. Checked: does the text give each new identifier with its type, access level, `async`/`throws`, and parameters; does it name each API and SwiftUI modifier with its arguments (the movie file output, the delegate and the continuation, the timer, the picker, the swipe gesture, the time view's font and colors); do boilerplate steps have the `copy` mark and a spec.

## Suggestions for the generator and the glossary

1. **Glossary: property observers (`didSet`).** Steps 7.2 and 7.7 are the first use of `var x = … { didSet { … } }` in the tutorial. A learner who does not know property observers cannot write the form from "a `didSet` observer". Suggested entry: pattern `/\b(didSet|willSet)\s*\{/`, title "didSet", text: "A property observer. The code in `didSet` runs each time the property gets a new value, after the value is stored. `oldValue` holds the old value."
2. **Glossary: the storage of a property wrapper (`_name`).** Steps 8.2 and 9.1 write `_direction = direction` and `_isRecording = isRecording` in an initializer. The underscore form is not in the glossary, and a learner writes `self.direction = direction`, which does not compile for a `@Binding`. Suggested entry: pattern `/^\s*_\w+\s*=/m`, title "`_name` (property wrapper storage)", text: "A property with a wrapper such as `@Binding` has a hidden storage property with an underscore. An initializer assigns the wrapper value to `_name`, not to `name`."
3. **Glossary: `switch` as an expression.** Step 1.3 (`systemName`) returns a `String` from a `switch` with no `return` statement, a Swift 5.9 form. A learner who writes `return` in each case gets a one-line diff. Suggested entry: pattern `/case\s+\.\w+:\s*\n\s*"[^"]*"\s*$/m` (a case whose body is one literal), title "switch expression", text: "A `switch` whose cases each have one expression can be the value of a property or a `return`. No `return` is needed in the cases."
4. **Generator: the first-highlighted-line placeholder.** On 6.1 and 7.2 the first fence line is highlighted, so the cover begins with `// your code goes here` and no context line above it. The "Inside …" text is missing, because the first new line is at type level. A line of context above the fence (the previous declaration) would help; writers can add it, or the generator can take one line from the file on `startBranch`.
5. **Validator: highlighted lines that repeat existing lines.** As in chapter 5 (finding 1 there) and here in 9.3: when git counts the tail of a block as added, the highlighted run contains lines that the learner already has. The check proposed in the chapter 5 review (compare a highlighted run with the file on `startBranch`, warn when no `remove` fence lists the repeated lines) would have found this one.
6. **Sample quirks that the page now asks the learner to keep.** The stray backtick at the end of the doc comment in `observeOutputServices()` (6.1), the comment "The vertical offset from center." on a horizontal offset (8.4), and `.tag($0.rawValue)` with a `CaptureMode` selection (8.2) are in the Apple sample. The page tells the learner to keep them so that the file equals the branch. If the coordinator prefers, the branch can be cleaned and the three sentences removed.
