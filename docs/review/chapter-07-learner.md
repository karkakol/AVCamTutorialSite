## Method

The same two personas as in the reviews of chapters 2 to 5 went through all 53 steps.

- **The copier** reads the code card and the delete boxes, pastes the highlighted lines at the place the fence shows, and builds at each checkpoint. Checked: is the place clear, is anything needed that no step says (file, group, import, Xcode action), do the delete boxes cover every line that `git diff chapter-06 chapter-07` removes or moves, is a line highlighted in two steps.
- **The self-implementer** uses the "Try first" mode. This person sees the instruction, the caption, the cover (file, "Inside …", context lines, placeholder, delete boxes, copy note), and the Swift notes, but not the code. Checked: does the text give each new identifier with its type, access level, `async`/`throws`, and parameters; does it name each API, callback, and SwiftUI modifier with its arguments (Live Photo, photo quality prioritization, the badge view, the menu); do boilerplate steps have the `copy` mark and a spec.

The cover text of each step was extracted from the rendered HTML and compared with `git show chapter-07:<file>` and the diff. The findings were fixed on the page in the same pass (instructions, captions, two `copy` marks; no main code fence and no `remove` fence changed). Then `npm run validate` and the replay ran.

Note on the build: a second Claude session worked on the site repository at the same time (it added the pictures `ch07-s5-5.jpg`, `ch07-s6-7.jpg`, `ch07-s6-8.jpg` and rebuilt `dist/`). Three of my builds lost the "Inside …" text on every page, and `dist/ch07-build.html` changed between two of my commands. A build that copied its output to a private folder in the same command had all 44 "Inside …" texts. The covers in this review are from that copy. See suggestion 3.

## Suggestions for the generator and the glossary

1. **Glossary: `Self` as a type, and `$0`.** Step 1.3 is the first use of `Self` as a return type (`var id: Self { self }`). A learner can read `Self` as `self`. Suggested entry: pattern `/\bSelf\b/`, title "Self", text: "The type of the current instance. In a protocol or an enumeration, it stands for the concrete type, so `var id: Self` returns a value of the enumeration." The shorthand argument `$0` has no entry either; its first use is chapter 3 (`outputServices.forEach { $0.updateConfiguration(for:) }`), so the card would go there, with a pointer at 6.3 here.
2. **Generator: a highlighted closing brace that already exists.** Step 3.6 highlights the `}` of `updateConfiguration(for:)` because git counts it as added. The cover handles it (the placeholder runs merge), but the code card shows an existing line as new. The validator could accept a fence that does not highlight such a brace when the same text exists on the line directly after the new lines on `startBranch`, or the generator could render a highlighted line that equals the next context line on `startBranch` without the highlight.
3. **Generator: builds that run next to another writer of `dist/`.** Three builds in this review lost all "Inside …" texts, and `dist/ch07-build.html` changed between two commands, while a second session also built the site. The build should print a warning when `repo.fileLines` fails for a fence (chapter 5 review, suggestion 3, still open), and a build could write to a temporary folder and rename it at the end, so a reader never sees a half-written `dist/`.
4. **Copy note and caption say the same thing twice.** As in the chapters 3 and 4 review (suggestion 2): on 1.7 and 5.5 the generator note and the caption sentence both say to copy the file. One of them is enough.
