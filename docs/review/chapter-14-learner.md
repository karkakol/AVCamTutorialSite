## Method

The same two personas as in the reviews of chapters 2 to 12 went through all 44 steps.

- **The copier** reads the code card and the delete boxes, pastes the highlighted lines at the place the fence shows, and builds at each checkpoint. Checked: is the place clear, is anything needed that no step says (import, Xcode action, target membership, deletion), does the delete box cover the one line that `git diff chapter-13 chapter-14` removes, is any line highlighted in two steps, does a highlighted run contain a line that already exists on `chapter-13`.
- **The self-implementer** uses the "Try first" mode. This person sees the instruction, the caption, the cover (file, "Inside …", context lines, placeholders, the comment lines of the solution as hints, delete box), and the Swift notes, but not the code. Checked: does the text give each new identifier with its type, access level, start value, `async`, and parameters; does it name each zoom API (`minAvailableVideoZoomFactor`, `maxAvailableVideoZoomFactor`, `virtualDeviceSwitchOverVideoZoomFactors`, `displayVideoZoomFactorMultiplier`, `ramp(toVideoZoomFactor:withRate:)`, `videoZoomFactor`, the key-value observation), the pinch gesture (`MagnifyGesture`, `onChanged`, `onEnded`, `magnification`), and the sizes and colors of the zoom control; does it give the string literals; does it say when the project does not compile or builds with warnings between steps.

The cover text of each of the 37 code steps was extracted from the rendered HTML (35 "Inside …" texts; the two covers at file level, 1.2 and 5.7, and the new-file cover 5.1 have none) and compared with `git diff chapter-13 chapter-14 -- '*.swift'`. The findings were fixed on the page in the same pass (captions only; no instruction, main code fence, `remove` fence, or `copy` mark changed). Then `npm run validate` and the replay ran.

## Suggestions for the generator and the glossary

1. **Glossary: a constant that hides a parameter.** Step 3.2 writes `let factor = min(max(factor, …), …)` inside a method whose parameter is `factor`. A learner who does not know that Swift permits this picks another name. Suggested entry: pattern `/^\s*let (\w+) = [^\n]*\b\1\b/m`, title "Shadowing a parameter", text: "A local constant can have the name of a parameter. From this line on, the name means the new constant." Link: the Swift book, "Functions" or "The Basics".
2. **Glossary: a synchronous method for an `async` requirement.** Step 4.8 satisfies `func setZoom(to:) async` of the protocol with a method without `async`. No entry covers this. The caption now says it; a glossary entry would make the sentence unnecessary in later chapters.
3. **Generator: string literals and special characters as hints.** Findings 4 and 13 are a string value and a special character (×, U+00D7) that only the solution shows. As suggested in the chapter 12 review (suggestion 3), the cover could show the string literals of the highlighted lines in the hint style.
4. **Generator: a step that breaks a protocol conformance.** Step 4.3 adds requirements to `Camera`, and the project does not compile until 4.8. The same pattern was on chapters 9 and 12. A fence attribute such as `compiles=no` would render a standard note instead of a caption sentence.
5. **Generator: a fence with highlighted lines in two declarations.** Step 5.9 highlights lines in `compactUI` and in `regularUI`, and the cover says only "Inside … › var compactUI: some View". A second "and inside …" for a later highlighted line in another declaration would help; the instruction covers it now.
6. **Validator: `NSNumber` arrays.** No tool can find this, but writers can: when a highlighted line maps `[NSNumber]` with `CGFloat(truncating:)`, the caption must say so. A note in `AUTHORING.md` under "Writing style" ("name the conversion when an API returns `NSNumber`") would help the next chapters.
