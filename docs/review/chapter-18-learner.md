## Method

The same two personas as in the reviews of chapters 2 to 16 went through all 44 steps.

- **The copier** reads the code card and the delete boxes, pastes the highlighted lines at the place the fence shows, and builds at each checkpoint. Checked: is the place clear, is anything needed that no step says (import, Xcode action, target membership, deletion), do the delete boxes cover the 17 lines that `git diff chapter-17 chapter-18` removes, is any line highlighted in two steps, does a highlighted run contain a line that already exists on `chapter-17`.
- **The self-implementer** uses the "Try first" mode. This person sees the instruction, the caption, the cover (file, "Inside …", context lines, placeholders, the comment lines and the string literals of the solution as hints, delete box), and the Swift notes, but not the code. For a new file, the cover says only "write the whole file yourself. The step text says what the file contains", so the caption must be the spec. Checked: does the text give each new identifier with its type, access level, start value, `async`, `throws`, parameters, and argument labels; does it name the data output API (`AVCaptureVideoDataOutput`, `AVCaptureAudioDataOutput`, `addOutputWithNoConnections(_:)`, `videoSettings` with `kCVPixelBufferPixelFormatTypeKey` and `kCVPixelFormatType_32BGRA`, `setSampleBufferDelegate(_:queue:)`, `recommendedVideoSettingsForAssetWriter(writingTo:)`, `recommendedAudioSettingsForAssetWriter(writingTo:)`, `ports(for:sourceDeviceType:sourceDevicePosition:)`), the delegate protocols and their one method `captureOutput(_:didOutput:from:)`, the Metal objects (`MTLCreateSystemDefaultDevice()`, `makeDefaultLibrary()`, `makeFunction(name:)`, `MTLComputePipelineState`, `MTLCommandQueue`, `MTLComputeCommandEncoder` with `setTexture(_:index:)`, `setBytes`, `dispatchThreadgroups`, `CVMetalTextureCache`, `CVPixelBufferPool`), the asset writer life cycle (`AVAssetWriter(outputURL:fileType:)`, `add(_:)`, `expectsMediaDataInRealTime`, `startWriting()`, `startSession(atSourceTime:)`, `isReadyForMoreMediaData`, `append(_:)`, `markAsFinished()`, `finishWriting()`, `error`), and the dispatch queue rules (one serial `dataOutputQueue` for the three outputs, `async` for the layout, `sync` for start and detach, `receive(on: sessionQueue)` for the published activity); does it say when the project does not compile or builds with warnings between steps.

The cover text of each of the 37 code steps was extracted from the rendered HTML (31 "Inside …" texts; the four new-file covers and the two file-level covers of 6.2 have none) and compared with `git diff chapter-17 chapter-18 -- '*.swift'` and `git show chapter-17:AVCam/CaptureService.swift`, `chapter-17:AVCam/Capture/MultiCamCapture.swift`. The findings were fixed on the page in the same pass: captions; `copy` marks on the eight fences of the Metal file and the mixer; one `highlight=` change (5.3, a highlighted line that already exists). ## Suggestions for the generator and the glossary

1. **Glossary: `===`.** Step 3.4 uses the identity operator, and no entry matches. Suggested entry: pattern `/\s===\s/`, title "=== (identity)", text: "Compares two references. The result is `true` when both names point to the same object, not when two objects have equal values." Link: the Swift book, "Basic Operators" or "Structures and Classes" ("Identity Operators").
2. **Glossary: `&` argument for a C function.** Steps 2.4, 2.5, 2.7, 2.8, and 3.6 pass `&pool`, `&buffer`, `&description`, `&cache`, `&parameters`, `&texture`, `&timing`, `&mixedSampleBuffer`. The `inout` entry matches the keyword only. Suggested entry: pattern `/\(.*&\w+/` restricted to C-style calls, or a second pattern on the `inout` entry, text: "The `&` gives the function the address of a variable. The function writes its result there. The variable must be `var`."
3. **Generator: "Inside …" for a fence that starts inside a method.** Six covers (2.5, 2.7, 4.4, 4.5, 5.3, 6.1) show only the class when the fence has no declaration line, or when highlighted lines are in two declarations. The suggestion from the chapter 14 review (a second "and inside …") applies; for a fence with no declaration line, the enclosing declaration of the first highlighted line in the branch file would serve.
4. **Generator: string hints on a new-file cover.** The cover of a `new` fence shows no "texts in this code" hint, so the kernel name (2.3) and the queue label (3.1) were invisible to the self-implementer. The same hint as on an existing-file cover would help; the captions give the strings now.
5. **Generator: `copy` on a fence with `highlight=`.** The note says "Copy this file as it is; the caption says what it contains". For the seven partial fences of the mixer, "Copy these lines as they are" would be more exact. A small wording change when the fence is not `new`.
6. **Generator: a step that breaks the build.** This page has six places (finding 4) where the project does not compile until a later step, and two with warnings (3.5, 4.6). The `compiles=no` or `warnings` fence attribute from the chapter 9, 12, 14, and 16 reviews would render a standard note.
7. **Validator: a highlighted line that exists on `startBranch`.** Finding 5 is a highlighted line that `git diff --unified=0` does not add. The validator could warn when a highlighted line (outside a `new` fence) is unchanged between `startBranch` and `branch` at that place; the replay accepts it, so only a learner notices.
8. **AUTHORING.md: new-file captions.** The "Try first" cover of a new file depends entirely on the caption. A sentence under "Writing style" ("for a `new` fence without `copy`, the caption lists every declaration with its type and access level") would prevent findings 2 and 3 in later chapters.
