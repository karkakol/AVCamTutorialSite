At the end of chapter 4, the app takes photos and saves them. But the preview fills all the space that it gets, and the toolbar lies on top of it. In this tutorial, you give the screen the layout of a camera.

You lock the iPhone interface to portrait. You give the preview a viewfinder frame with the shape of the photo. Then you split the camera interface into a compact layout for iPhone and a regular layout for iPad, and you calculate the position of the toolbar from the size of the window.

This chapter has no new capture code. All changes are in the SwiftUI views and in one build setting. Read [Concepts: layout](ch05-concepts.md) first. It explains why a camera screen has this layout.

## Prepare the project for two layouts

In this section, you make two small changes that the other sections build on.

The first change is a build setting. Xcode writes it to the project file, `AVCam.xcodeproj/project.pbxproj`. You do not edit this file by hand, so no step shows its contents.

The second change is the `PlatformView` protocol. A view that adopts it can ask one question: "is this window large or small?" The answer comes from the two size classes of SwiftUI.

### Step
Open the Build Settings tab of the `AVCam` target. In the Info.plist Values group, remove the two landscape orientations for iPhone.

The interface of the app now stays in portrait when the person turns the iPhone. The viewfinder does not turn or change its size while the person frames a picture, and the app needs only one iPhone layout. Photos are still level: the rotation coordinator from chapters 2 and 3 gives the capture angle to the photo output, and that angle does not depend on the interface. Do not change the iPad setting. An iPad app must work in each orientation.

> [!TIP]
> Type "orientations" in the filter field of the Build Settings tab to find the two settings.

```settings title="Target AVCam › Build Settings › Info.plist Values"
Supported Interface Orientations (iPhone): Portrait
Supported Interface Orientations (iPad): no change (all four orientations)
Value in the project file: UIInterfaceOrientationPortrait
```

### Step
In `ViewExtensions.swift`, add the `PlatformView` protocol with the two size class requirements `verticalSizeClass` and `horizontalSizeClass` below the `largeButtonSize` constant.

The protocol refines `View`. The two requirements are read-only properties (`{ get }`) of the type `UserInterfaceSizeClass?`. A view that adopts this protocol must have the two properties. The view gets their values from the SwiftUI environment. Mark the protocol `@MainActor`, because `View` is on the main actor too.

```swift file=AVCam/Support/ViewExtensions.swift highlight=3-7
let largeButtonSize = CGSize(width: 64, height: 64)

@MainActor
protocol PlatformView: View {
    var verticalSizeClass: UserInterfaceSizeClass? { get }
    var horizontalSizeClass: UserInterfaceSizeClass? { get }
}

struct DefaultButtonStyle: ButtonStyle {
```

### Step
Add two read-only `Bool` requirements to the protocol: `isRegularSize` and `isCompactSize`.

These are the two questions that the views ask. A requirement in the protocol, together with a default implementation in an extension, lets a view supply its own answer if it must.

```swift file=AVCam/Support/ViewExtensions.swift highlight=5-6
@MainActor
protocol PlatformView: View {
    var verticalSizeClass: UserInterfaceSizeClass? { get }
    var horizontalSizeClass: UserInterfaceSizeClass? { get }
    var isRegularSize: Bool { get }
    var isCompactSize: Bool { get }
}
```

### Step
Below the protocol, add an extension of `PlatformView` with the default implementations of the two properties.

A window is regular only when the two size classes are `.regular`. It is compact when one or the two of them are `.compact`. Each property is one comparison, with `&&` for regular and `||` for compact. The two properties are not exact opposites: before SwiftUI supplies the size classes, the values are `nil`, and the two properties are `false`. You use `isCompactSize` in chapter 9.

```swift file=AVCam/Support/ViewExtensions.swift highlight=9-12
@MainActor
protocol PlatformView: View {
    var verticalSizeClass: UserInterfaceSizeClass? { get }
    var horizontalSizeClass: UserInterfaceSizeClass? { get }
    var isRegularSize: Bool { get }
    var isCompactSize: Bool { get }
}

extension PlatformView {
    var isRegularSize: Bool { horizontalSizeClass == .regular && verticalSizeClass == .regular }
    var isCompactSize: Bool { horizontalSizeClass == .compact || verticalSizeClass == .compact }
}

struct DefaultButtonStyle: ButtonStyle {
```

## Give the preview a viewfinder frame

The photo has the aspect ratio 3:4 in portrait. In this section, `PreviewContainer` gives the preview the same ratio. Then the preview layer has the shape of the image, and the person sees exactly what the photo contains.

The container does this only in a narrow window. In a wide window, the preview fills all the space.

![The compact layout: a 3:4 viewfinder frame that is moved up by 44 points, with the toolbar in the black bar below it](../images/ch05-compact-layout.svg)

### Step
In `PreviewContainer.swift`, add the type alias `AspectRatio` and the two global constants `photoAspectRatio` and `movieAspectRatio` above the `PreviewContainer` structure.

`AspectRatio` is another name for `CGSize`. The camera sensor has the ratio 4:3, and a video usually has the ratio 16:9. The interface is in portrait, so the constants hold the turned values: `AspectRatio(width: 3.0, height: 4.0)` for the photo and `AspectRatio(width: 9.0, height: 16.0)` for the movie. They are global constants, because `CameraUI` uses the video ratio later in this chapter.

```swift file=AVCam/Views/PreviewContainer.swift highlight=3-6

let photoAspectRatio = AspectRatio(width: 3.0, height: 4.0)
let movieAspectRatio = AspectRatio(width: 9.0, height: 16.0)

/// A view that provides a container view around the camera preview.
```

In this section, you move that stack into a property with the name `compactUI`, and you add a second property, `regularUI`, for a large window. The `body` property selects one of them. This is the rewrite of `CameraUI`, in four steps.

## Put the toolbar in its position

The toolbar is at the bottom edge of the layout area. In the sample, it sits higher in the black bar below the frame, with empty space below it. The sample calculates the space below the toolbar from the size of the window.

In this section, you measure the window, calculate the space, and apply it. Then you make the toolbar and the camera view adopt `PlatformView`.

### Step
In `CameraUI.swift`, add the private `@State` property `windowSize`, a `CGSize`, below the two size class properties.

Start with `CGSize.zero`. The value is zero until SwiftUI measures the view for the first time. It is a `@State` property, so the view updates when the value changes.

```swift file=AVCam/Views/CameraUI.swift highlight=4-5
    @Environment(\.verticalSizeClass) var verticalSizeClass
    @Environment(\.horizontalSizeClass) var horizontalSizeClass
    
    // The size of the window that contains the camera UI.
    @State private var windowSize = CGSize.zero
    
    var body: some View {
```

### Step
Add the `onGeometryChange(for:of:action:)` modifier to the `Group`, between the group and the overlay. Calculate the size of the window, and store it.

- The `for:` argument is the type of the value, `CGSize.self`. The first closure gets a geometry proxy and returns a value. SwiftUI calls the second closure, `action:`, when that value changes, for example when the person resizes the window on iPad. The action stores the value in `windowSize`.
- `proxy.size` is the size of the layout area. That area does not include the safe areas, such as the area of the home indicator. The closure adds `proxy.safeAreaInsets` (`leading` and `trailing` to the width, `top` and `bottom` to the height) to get the full window.

The sample measures the window, and not the screen, because an iPad window can be smaller than the screen.

```swift file=AVCam/Views/CameraUI.swift highlight=9-17
    var body: some View {
        Group {
            if isRegularSize {
                regularUI
            } else {
                compactUI
            }
        }
        // Measure the window that contains the UI. The geometry proxy reports the layout area,
        // which excludes the safe areas, so add those insets back to determine the window size.
        .onGeometryChange(for: CGSize.self) { proxy in
            let insets = proxy.safeAreaInsets
            return CGSize(width: proxy.size.width + insets.leading + insets.trailing,
                          height: proxy.size.height + insets.top + insets.bottom)
        } action: { size in
            windowSize = size
        }
        .overlay {
            StatusOverlayView(status: camera.status)
        }
    }
```

### Step
At the end of the structure, add the computed property `bottomPadding` of the type `CGFloat`, which calculates the space below the toolbar.

- `CGRect(origin: .zero, size: windowSize)` is the bounds of the window.
- `AVMakeRect(aspectRatio:insideRect:)` with `movieAspectRatio` returns the largest rectangle with the given ratio that fits in the center of the bounds. Here, it is the area of a 9:16 video in the window.
- `rect.minY` is the top edge of that area. It is also the height of the bar above the video.
- The space below the toolbar is half of that height, rounded with `rounded()` before the division, plus 12 points. Thus the space is larger in a tall window.

The property always uses the video ratio, also in photo mode. So the toolbar does not move when the capture mode changes in chapter 8.

```swift file=AVCam/Views/CameraUI.swift highlight=5-10
            .padding(.bottom, 32)
        }
    }
    
    var bottomPadding: CGFloat {
        // Dynamically calculate the offset for the bottom toolbar in iOS.
        let bounds = CGRect(origin: .zero, size: windowSize)
        let rect = AVMakeRect(aspectRatio: movieAspectRatio, insideRect: bounds)
        return (rect.minY.rounded() / 2) + 12
    }
}
```

## Check your understanding

### The iPhone interface of AVCam is locked to portrait. The person holds the iPhone in landscape and takes a photo. Why is the photo a landscape photo?

- [ ] Because the system turns the interface for a short time when the capture starts.
  > The interface never turns to an orientation that the app does not support.
- [x] Because the capture angle of the rotation coordinator follows gravity, not the interface.
  > Correct. The coordinator has two angles. The preview angle follows the interface, and stays the same. The capture angle changes when the person turns the camera, and the app sets it on the photo output.
- [ ] Because the preview layer rotates the image before the photo output gets it.
  > The preview layer and the photo output have separate connections. The rotation of the preview has no effect on the photo.

### Why does `PreviewContainer` give the preview the aspect ratio 3:4, when it could set the video gravity of the layer to `.resizeAspectFill`?

- [ ] Because a layer with `.resizeAspectFill` changes the shape of the image.
  > That is the `.resize` value. `.resizeAspectFill` keeps the shape of the image.
- [ ] Because a SwiftUI view cannot contain a layer that fills the screen.
  > It can. In chapters 1 to 4, the preview filled the layout area of the screen.
- [x] Because a frame with the shape of the photo shows all of the photo, and `.resizeAspectFill` cuts a part of it.
  > Correct. With the 3:4 frame, the person sees exactly what the photo contains. With a fill, the photo contains things that were not on the screen.

### A window has a compact horizontal size class and a regular vertical size class. Which layout does `CameraUI` show?

```swift
var isRegularSize: Bool { horizontalSizeClass == .regular && verticalSizeClass == .regular }
```

- [x] The compact layout, because `isRegularSize` is `true` only when the two size classes are regular.
  > Correct. This is an iPhone in portrait, and also a narrow window on iPad. In the two situations, there is no space for the panel of 740 points.
- [ ] The regular layout, because one regular size class is sufficient.
  > The property uses `&&`. One compact size class makes it `false`.
- [ ] No layout, because the two size classes must be equal.
  > `body` has an `if` statement with an `else` branch. It always shows one of the two layouts.
