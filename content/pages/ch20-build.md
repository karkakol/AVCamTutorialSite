In this tutorial, the dual mode records a movie. The movie shows what the screen shows: one camera fills the frame, and the other camera is a small picture in a corner. A tap on the preview exchanges the two pictures on the screen and in the recording. The record button and the recording time of the video mode come back for the dual mode.

You add four files to the `Capture` group: `MovieRecorder.swift`, which writes a movie file with an [`AVAssetWriter`](https://developer.apple.com/documentation/avfoundation/avassetwriter); `PiPMixer.metal`, a compute kernel that draws the small picture into the full picture; `PiPVideoMixer.swift`, which runs the kernel; and `DualRecorder.swift`, which receives the frames of the outputs and connects the three parts. You also add approximately 170 lines to eight files that you know from the earlier chapters.

This chapter is a part of "Beyond the sample". The code is not in the Apple sample. The design follows the Apple sample [AVMultiCamPiP](https://developer.apple.com/documentation/avfoundation/avmulticampip-capturing-from-multiple-cameras), which has a mixer and a recorder of the same shape. Read [Concepts: record picture in picture](ch20-concepts.md) first if you want the background for each step.

> [!IMPORTANT]
> The test for this tutorial ran in the iPhone 18 Pro simulator (iOS 27.0) with SimCam. There, a recording of 10.8 seconds produced a movie of 640 by 480 pixels in the Photos library, with the small picture at the top left. The movie had no audio track, because the simulator reports audio settings with a sample rate of 0. Nobody ran this chapter on a real iPhone. So the audio track, the HEVC compression settings, and the costs of the three outputs are not verified on hardware.

The four new files need one change in the Xcode interface. The capture extension from chapter 15 compiles `CaptureService.swift`, which uses `MultiCamCapture`, which uses the new types. So the four files must also belong to the extension target, as the two files of chapter 19 do. Xcode writes this to the project file, `AVCam.xcodeproj/project.pbxproj`. You do not edit this file by hand, so no step shows it.

## Write the movie recorder

In chapter 10, `AVCaptureMovieFileOutput` compressed the frames and wrote the file by itself. The mixed frames of the dual mode exist in no connection, so the app writes the file itself. In this section, you write `MovieRecorder`, a small class around an `AVAssetWriter` with a video input and an optional audio input. Nothing uses the class yet, so the section ends with a build.

### Step
Create a new Swift file with the name `MovieRecorder.swift` in the `Capture` group, and replace its contents.

The file starts with the license header and `import AVFoundation`. It declares `final class MovieRecorder` with three stored properties: `private let writer: AVAssetWriter`, `private let videoInput: AVAssetWriterInput`, and `private let audioInput: AVAssetWriterInput?`. A computed property `var outputURL: URL` returns `writer.outputURL`. The initializer is `init(videoSettings: [String: Any], audioSettings: [String: Any]?) throws`. It creates the writer with `AVAssetWriter(outputURL: .movieFileURL, fileType: .mov)`, which throws: `URL.movieFileURL` is the extension from chapter 10, and `.mov` is the QuickTime file type. Each track is an [`AVAssetWriterInput`](https://developer.apple.com/documentation/avfoundation/avassetwriterinput) with `mediaType:` and `outputSettings:` from the caller, and `writer.add(_:)` puts it in the writer. [`expectsMediaDataInRealTime`](https://developer.apple.com/documentation/avfoundation/avassetwriterinput/expectsmediadatainrealtime) tells the writer that the samples come from live capture, so it must not wait for a full buffer. The audio input exists only when the caller gives audio settings (`if let audioSettings`); otherwise `audioInput` is `nil`.

```swift file=AVCam/Capture/MovieRecorder.swift new
/*
See the LICENSE.txt file for this sample's licensing information.

Abstract:
An object that writes video and audio sample buffers to a movie file.
*/

import AVFoundation

/// An object that writes sample buffers to a QuickTime movie file with an asset writer.
///
/// `AVCaptureMovieFileOutput` does this work by itself for one camera. For frames that the app makes
/// itself, the app has to write the file. `DualRecorder` calls this object on the data output queue.
final class MovieRecorder {
    
    private let writer: AVAssetWriter
    private let videoInput: AVAssetWriterInput
    private let audioInput: AVAssetWriterInput?
    
    /// The location of the movie file.
    var outputURL: URL { writer.outputURL }
    
    /// Creates a recorder that writes to a new temporary file.
    ///
    /// - Parameters:
    ///   - videoSettings: The compression settings for the video track, from the video data output.
    ///   - audioSettings: The compression settings for the audio track, or `nil` for a movie without sound.
    init(videoSettings: [String: Any], audioSettings: [String: Any]?) throws {
        writer = try AVAssetWriter(outputURL: .movieFileURL, fileType: .mov)
        
        // The inputs receive the frames in real time, so the writer must not wait for a full buffer.
        videoInput = AVAssetWriterInput(mediaType: .video, outputSettings: videoSettings)
        videoInput.expectsMediaDataInRealTime = true
        writer.add(videoInput)
        
        if let audioSettings {
            let input = AVAssetWriterInput(mediaType: .audio, outputSettings: audioSettings)
            input.expectsMediaDataInRealTime = true
            writer.add(input)
            audioInput = input
        } else {
            audioInput = nil
        }
    }
}
```

### Step
Below the initializer, add the `append(videoSampleBuffer:)` method. The first video frame starts the file and sets its time zero.

The signature is `func append(videoSampleBuffer: CMSampleBuffer)`, with no `async` and no `throws`. `startWriting()` opens the file one time, when `writer.status` is still `.unknown`. After that, the status is `.writing`, and the guard needs that status. Then [`startSession(atSourceTime:)`](https://developer.apple.com/documentation/avfoundation/avassetwriter/startsession(atsourcetime:)) takes the time stamp of the first frame as the time zero of the movie. With a time zero of 0, the movie would start with a long empty gap. Before the `append`, the code checks [`isReadyForMoreMediaData`](https://developer.apple.com/documentation/avfoundation/avassetwriterinput/isreadyformoremediadata): the SDK header permits an `append` only while the value is `true`, and for a live source a dropped frame is the better choice.

```swift file=AVCam/Capture/MovieRecorder.swift highlight=3-12

    func append(videoSampleBuffer: CMSampleBuffer) {
        if writer.status == .unknown {

            writer.startWriting()
```

## Write the Metal mixer

The mixer draws the small picture into the full picture. It does this on the GPU with a compute kernel: a function that runs one time for each pixel of the output. In this section, you write the kernel in the Metal shading language, and then the Swift class that gives the kernel its textures and runs it. Two files, one job.

### Step
Create a new Metal file with the name `PiPMixer.metal` in the `Capture` group, and replace its contents with the parameters and the sampler.

Use the Metal File template. This file and the next one are boilerplate: copy them as they are. `MixerParameters` is the structure that the Swift code fills: two `float2` members, `smallPicturePosition` and `smallPictureSize`, the position and the size of the small picture in pixels of the output. The Swift copy must have the same layout. The sampler `linearSampler` is a `constant sampler` with `filter::linear`, `coord::pixel`, and `address::clamp_to_edge`: it scales the small picture down with linear filtering, and it reads the texture in pixel coordinates. The [Metal Shading Language Specification](https://developer.apple.com/metal/Metal-Shading-Language-Specification.pdf) describes both.

```objc file=AVCam/Capture/PiPMixer.metal new copy

/// The position and size of the small picture, in pixels of the output texture.
struct MixerParameters {
    float2 smallPicturePosition;
    float2 smallPictureSize;
};

/// A sampler that scales the small picture with linear filtering.
constant sampler linearSampler(filter::linear, coord::pixel, address::clamp_to_edge);
```

### Step
Below the sampler, add the kernel `pictureInPictureMixer`. It writes one output pixel for each thread.

The kernel gets three `texture2d<half>` textures and the parameters: `fullPicture` with `access::read` at `texture(0)`, `smallPicture` with `access::sample` at `texture(1)`, `output` with `access::write` at `texture(2)`, and `const device MixerParameters&` at `buffer(0)`. The Swift code uses the same indexes. The last parameter, `uint2 position [[ thread_position_in_grid ]]`, is the pixel that this thread writes. The GPU runs the kernel in groups of threads, and the last groups can reach beyond the edge of the texture, so the first test returns for a position outside the output. Inside the frame of the small picture, the kernel maps the output pixel to a pixel of the small picture and lets the sampler scale it down. Everywhere else, it copies the pixel of the full picture.

```objc file=AVCam/Capture/PiPMixer.metal highlight=3-29 copy
constant sampler linearSampler(filter::linear, coord::pixel, address::clamp_to_edge);

/// Writes one output pixel: from the small picture inside its frame, from the full picture elsewhere.
kernel void pictureInPictureMixer(texture2d<half, access::read> fullPicture [[ texture(0) ]],
                                  texture2d<half, access::sample> smallPicture [[ texture(1) ]],
                                  texture2d<half, access::write> output [[ texture(2) ]],
                                  const device MixerParameters& parameters [[ buffer(0) ]],
                                  uint2 position [[ thread_position_in_grid ]]) {
    // Stay inside the output texture; the grid can be larger than the texture.
    if (position.x >= output.get_width() || position.y >= output.get_height()) {
        return;
    }
    
    uint2 origin = uint2(parameters.smallPicturePosition);
    uint2 size = uint2(parameters.smallPictureSize);
    bool insideSmallPicture = position.x >= origin.x && position.y >= origin.y &&
                              position.x < origin.x + size.x && position.y < origin.y + size.y;
    
    half4 color;
    if (insideSmallPicture) {
        // Map the output pixel to a pixel of the small picture, which the sampler scales down.
        float2 scale = float2(smallPicture.get_width(), smallPicture.get_height()) / parameters.smallPictureSize;
        float2 source = float2(position - origin) * scale;
        color = smallPicture.sample(linearSampler, source + 0.5);
    } else {
        color = fullPicture.read(position);
    }
    output.write(color, position);
}
```

### Step
Create a new Swift file with the name `PiPVideoMixer.swift` in the `Capture` group, and replace its contents.

This file is boilerplate too; the six steps of this file show it in parts. The class is `final class PiPVideoMixer`. The private Swift `MixerParameters` has the same layout as the Metal structure: two `SIMD2<Float>` members with the same names. `var smallPictureFrame` is a `CGRect` (0.04, 0.03, 0.3, 0.3): the frame of the small picture as a part of the full picture, from 0 to 1. Two `private(set)` properties, `isPrepared` (`false`) and `outputFormatDescription` (`CMFormatDescription?`), tell the recorder the state. The Metal objects are `private`: `device` from `MTLCreateSystemDefaultDevice()`, and the optionals `commandQueue`, `pipelineState`, `textureCache`, and `outputPool`. The initializer compiles the kernel one time with `makeFunction(name: "pictureInPictureMixer")` and `makeComputePipelineState(function:)`: [`makeDefaultLibrary()`](https://developer.apple.com/documentation/metal/mtldevice/makedefaultlibrary()) loads every `.metal` file of the target, and the [`MTLComputePipelineState`](https://developer.apple.com/documentation/metal/mtlcomputepipelinestate) is the compiled kernel, ready to run. The pool, the texture cache, and the output format come later, because they depend on the size of the frames.

```swift file=AVCam/Capture/PiPVideoMixer.swift new copy
/*
See the LICENSE.txt file for this sample's licensing information.

Abstract:
An object that draws the frames of two cameras into one frame with Metal.
*/

import CoreMedia
import CoreVideo
import Metal

/// An object that draws a small picture from one camera into the full picture of the other camera.
///
/// The mixer runs a Metal compute kernel for each frame. `DualRecorder` calls it on the data output queue.
final class PiPVideoMixer {
    
    /// The parameters that the kernel reads. The layout must match the `MixerParameters` struct in the shader.
    private struct MixerParameters {
        var smallPicturePosition: SIMD2<Float>
        var smallPictureSize: SIMD2<Float>
    }
    
    /// The frame of the small picture, as a part of the full picture (0 to 1 in each direction).
    var smallPictureFrame = CGRect(x: 0.04, y: 0.03, width: 0.3, height: 0.3)
    
    /// A Boolean value that indicates whether the mixer has a buffer pool for the current frame size.
    private(set) var isPrepared = false
    
    /// The format of the frames that the mixer produces.
    private(set) var outputFormatDescription: CMFormatDescription?
    
    private let device = MTLCreateSystemDefaultDevice()
    private var commandQueue: MTLCommandQueue?
    private var pipelineState: MTLComputePipelineState?
    private var textureCache: CVMetalTextureCache?
    private var outputPool: CVPixelBufferPool?
    
    init() {
        // Compile the kernel one time. The default library contains every `.metal` file of the target.
        guard let device, let library = device.makeDefaultLibrary(),
              let function = library.makeFunction(name: "pictureInPictureMixer") else { return }
        commandQueue = device.makeCommandQueue()
        pipelineState = try? device.makeComputePipelineState(function: function)
    }
}
```

### Step
Below the initializer, add the `prepare(with:)` method. It creates a pool of output buffers with the size of the input frames.

A [`CVPixelBufferPool`](https://developer.apple.com/documentation/corevideo/cvpixelbufferpool) reuses buffers that the writer has released, so the app allocates no memory for each frame. The attributes dictionary has four keys: `kCVPixelBufferPixelFormatTypeKey` with `kCVPixelFormatType_32BGRA`, the format that the kernel writes; `kCVPixelBufferWidthKey` and `kCVPixelBufferHeightKey` from `CMVideoFormatDescriptionGetDimensions`; and `kCVPixelBufferIOSurfacePropertiesKey` with an empty dictionary, which lets the GPU and the asset writer share a buffer without a copy. Each key needs `as String`. `CVPixelBufferPoolCreate` is a C function: it returns a status and writes the pool to the `&pool` argument. The method ends after the pool for now; the next step completes it. The method calls `reset()`, which the next step adds, so the project does not compile until then.

```swift file=AVCam/Capture/PiPVideoMixer.swift highlight=3-22 copy

    // MARK: - Preparation
    
    /// Creates a pixel buffer pool and a texture cache for frames of the given format.
    func prepare(with formatDescription: CMFormatDescription) {
        reset()
        guard let device else { return }
        
        // The output frames have the size and the pixel format of the input frames.
        let dimensions = CMVideoFormatDescriptionGetDimensions(formatDescription)
        let attributes: [String: Any] = [
            kCVPixelBufferPixelFormatTypeKey as String: kCVPixelFormatType_32BGRA,
            kCVPixelBufferWidthKey as String: Int(dimensions.width),
            kCVPixelBufferHeightKey as String: Int(dimensions.height),
            // An IOSurface lets Metal and the asset writer share the buffer without a copy.
            kCVPixelBufferIOSurfacePropertiesKey as String: [:]
        ]
        var pool: CVPixelBufferPool?
        guard CVPixelBufferPoolCreate(nil, nil, attributes as CFDictionary, &pool) == kCVReturnSuccess, let pool else { return }
        outputPool = pool
    }
}
```

### Step
Complete `prepare(with:)` with the output format and the texture cache, and add the `reset()` method below it.

The asset writer needs a format description for each mixed frame. The simplest source is a first buffer from the pool: `CVPixelBufferPoolCreatePixelBuffer` makes it, and `CMVideoFormatDescriptionCreateForImageBuffer(allocator:imageBuffer:formatDescriptionOut:)` describes it. `CVMetalTextureCacheCreate(nil, nil, device, nil, &cache)` makes the cache. A [`CVMetalTextureCache`](https://developer.apple.com/documentation/corevideo/cvmetaltexturecache) turns a pixel buffer into a Metal texture that shares its memory. `reset()` discards all three, so that a new frame size gets a new pool.


### Step
Complete `mix(fullPicture:smallPicture:)` with the encoder, the thread groups, and the wait for the GPU.

A command buffer from `commandQueue.makeCommandBuffer()` gives an [`MTLComputeCommandEncoder`](https://developer.apple.com/documentation/metal/mtlcomputecommandencoder) with `makeComputeCommandEncoder()`. The encoder gets the pipeline state (`setComputePipelineState`), the three textures at the indexes of the kernel (`setTexture(_:index:)` with 0, 1, 2), and the parameters as bytes (`setBytes(&parameters, length: MemoryLayout<MixerParameters>.size, index: 0)`). The pipeline state tells the best width of a thread group (`threadExecutionWidth`) and the largest group size (`maxTotalThreadsPerThreadgroup`); the division rounds up, so that the groups cover every pixel. `dispatchThreadgroups(_:threadsPerThreadgroup:)` takes two `MTLSize` values, and `endEncoding()` closes the encoder. `commit()` sends the work to the GPU, and `waitUntilCompleted()` blocks until the frame is complete. A production app would use a completion handler and more buffers instead; the wait is simple and correct.

```swift file=AVCam/Capture/PiPVideoMixer.swift highlight=3-25 copy

        guard let commandBuffer = commandQueue.makeCommandBuffer(),
              let encoder = commandBuffer.makeComputeCommandEncoder() else { return nil }
        encoder.setComputePipelineState(pipelineState)
        encoder.setTexture(fullTexture, index: 0)
        encoder.setTexture(smallTexture, index: 1)
        encoder.setTexture(outputTexture, index: 2)
        encoder.setBytes(&parameters, length: MemoryLayout<MixerParameters>.size, index: 0)
        
        // Split the output into thread groups that fit the GPU.
        let width = pipelineState.threadExecutionWidth
        let height = pipelineState.maxTotalThreadsPerThreadgroup / width
        let threadsPerGroup = MTLSize(width: width, height: height, depth: 1)
        let groups = MTLSize(width: (outputTexture.width + width - 1) / width,
                             height: (outputTexture.height + height - 1) / height,
                             depth: 1)
        encoder.dispatchThreadgroups(groups, threadsPerThreadgroup: threadsPerGroup)
        encoder.endEncoding()
        
        // Wait for the GPU, so that the frame is complete when the writer reads it.
        commandBuffer.commit()
        commandBuffer.waitUntilCompleted()
        return output
    }
```

## Write the dual recorder

The dual recorder is the delegate of the three data outputs. It receives each frame and each block of audio samples on one serial queue, sorts the frames by camera, mixes the two pictures, and gives the result to the movie recorder. In this section, you write the class. The session gets its outputs in the next section.

### Step
Create a new Swift file with the name `DualRecorder.swift` in the `Capture` group, and replace its contents.

The file starts with the license header, `import AVFoundation`, and `import Combine`; without the second import, the compiler does not know `@Published`. The class adopts the two delegate protocols, [`AVCaptureVideoDataOutputSampleBufferDelegate`](https://developer.apple.com/documentation/avfoundation/avcapturevideodataoutputsamplebufferdelegate) and [`AVCaptureAudioDataOutputSampleBufferDelegate`](https://developer.apple.com/documentation/avfoundation/avcaptureaudiodataoutputsamplebufferdelegate), which need an `NSObject`. The class is `final class DualRecorder: NSObject` with the two protocols. `@Published private(set) var captureActivity: CaptureActivity = .idle` is published, like in `MovieCapture` from chapter 10, so the capture service can show the recording time. `let dataOutputQueue = DispatchQueue(label: "com.karolkakol.AVCam.dataOutputQueue")` is the serial queue of all three outputs: one queue means that no two delegate calls run at the same time, so the class needs no lock. `var smallPicture = AVCaptureDevice.Position.front` names the camera in the small picture. The recorder keeps the three outputs as `private let` constants, `backOutput` and `frontOutput` of type `AVCaptureVideoDataOutput` and `audioOutput` of type `AVCaptureAudioDataOutput?`, because the delegate method tells only the output that a frame comes from; the initializer `init(backOutput:frontOutput:audioOutput:)` stores them. The private state is `let mixer = PiPVideoMixer()`, `var recorder: MovieRecorder?`, `var latestSmallPictureFrame: CMSampleBuffer?`, `var recordingStartTime: CMTime?`, and `var reportedDuration = TimeInterval.zero`. The computed property `var isRecording: Bool` returns `recorder != nil`.

The signature is `func stopRecording() async throws -> Movie`, the same as in `MovieCapture`. Without a recorder, the method throws `MovieCaptureError.notRecording`. The order matters. After it, no frame reaches the movie recorder. Then `finish()` runs on the capture actor and waits for the writer, and the method returns `Movie(url:)` with the URL. A frame that arrives during `finishWriting()` would be an error, and the order makes that impossible.

```swift file=AVCam/Capture/MultiCamCapture.swift highlight=3-12
    }
    
    /// Stops the recording and returns the movie.
    func stopRecording() async throws -> Movie {
        guard let recorder else { throw MovieCaptureError.notRecording }
        // Detach the movie recorder on the data output queue, so that no frame arrives after this point.
        guard let movieRecorder = recorder.dataOutputQueue.sync(execute: { recorder.stopRecording() }) else {
            throw MovieCaptureError.notRecording
        }
        let url = try await movieRecorder.finish()
        return Movie(url: url)
    }
```

## Check your understanding

### The video mode records with `AVCaptureMovieFileOutput`. Why does the dual mode need `MovieRecorder` with an `AVAssetWriter` instead?

- [ ] A multi-camera session accepts no movie file output.
  > The type of the session is not the reason. The reason is in the frames.
- [x] A movie file output records the frames of one connection, and the mixed frames of the dual mode exist in no connection. The app makes them, so the app must write them.
  > Correct. The data outputs give the app the frames of each camera, the mixer makes a new frame, and the asset writer writes it to a file. The video mode keeps its movie file output.
- [ ] A movie file output cannot write a QuickTime file with an audio track.
  > It can, and it did in chapter 10. The movie file output is limited to the frames that a connection delivers.

### In the simulator, the recorded movie has no audio track. Which line is the reason, and why is it there?

- [ ] `let microphone = try? deviceLookup.defaultMic`. The simulator has no microphone, so `defaultMic` throws.
  > The simulator has a microphone input, and the session connects it. The audio output delivers nothing, but the input exists.
- [x] `if (audioSettings?[AVSampleRateKey] as? Double ?? 0) <= 0 { audioSettings = nil }`. In the simulator, the recommended audio settings had a sample rate of 0, and an `AVAssetWriterInput` with that value raised an exception.
  > Correct. The first version of this chapter crashed at the start of each recording. The guard records without sound instead. On a real iPhone, the settings are probably valid, but nobody verified that.
- [ ] `audioOutput.setSampleBufferDelegate(recorder, queue: recorder.dataOutputQueue)`. The audio output needs its own queue.
  > One serial queue for all outputs is correct. It is the reason why the recorder needs no lock.

### `MultiCamCapture.stopRecording()` first calls `recorder.stopRecording()` with `sync` on the data output queue, and then `movieRecorder.finish()`. Why this order?

- [ ] `finish()` must run on the data output queue, and `sync` puts it there.
  > `finish()` runs on the capture actor, after the `sync` block. The `sync` block only detaches the movie recorder.
- [x] The detach happens between two frames on the data output queue, so no frame reaches the writer after it. Then `finish()` can close the file with no frame in flight.
  > Correct. A frame that arrives during `finishWriting()` would be an error. The detach first, then the finish, makes that impossible.
- [ ] `recorder.stopRecording()` writes the index of the file, and `finish()` only returns the URL.
  > `recorder.stopRecording()` writes nothing. It sets `recorder` to `nil` and returns the movie recorder. `finish()` closes the inputs and waits for `finishWriting()`.
